# eval_seal_models audit (services/runtime/evaluation/seal.py, models.py, __init__.py)

## FIXED
1. seal.py:~88 (`verify_evidence_seal`): the safety-gate check ran only when `decision == "PROMOTED"`, so any other decision string (`"promoted"`, `"PROMOTED "`, `"LGTM"`, `""`) with a failed mandatory gate verified as "authentic, untampered, and structurally verified". Tests: `test_unrecognized_decision_does_not_bypass_safety_gate_check`, `test_unrecognized_decision_never_verifies_as_authentic`. Fix: after the hash check, a decision outside `{"PROMOTED","REJECTED"}` (the documented values; all 8 stored seals use PROMOTED) returns `(False, "Integrity violation! ...")`. Hash and gate logic are otherwise unchanged.
2. seal.py:~34 (`compute_canonical_hash`): `json.dumps` accepted NaN/Infinity, but pydantic `model_dump_json` (used to persist seals, e.g. scripts/demo_v7.py) writes them as `null`. A seal minted with a NaN metric hashed `NaN`, then failed verification with a false "Tamper detected!" after the persistence round trip (reproduced). Tests: `test_non_finite_metric_cannot_mint_unverifiable_seal`, `test_tampering_with_non_finite_value_reports_tamper_not_exception`. Fix: `allow_nan=False` so such a seal cannot be minted (ValueError, same fail-loud behaviour as set/datetime values); `verify_evidence_seal` catches that ValueError and reports tamper rather than raising. Digests for all finite inputs are unchanged (`test_seal_hash_is_stable_for_finite_values`, existing stored seals still verify).

## UNVERIFIED/NEEDS OTHER OWNER
- seal.py:85-91: a PROMOTED seal with an empty `safety_gate_results` verifies as valid. The set of mandatory gate names is not defined anywhere in code (ADR V7-ADR-003 names none), so requiring specific gates would be a design change.
- seal.py:11 (`EvidenceSealV1`): pydantic ignores extra fields, so unknown keys in a stored file are not covered by the hash, and `decision` is a free `str` (no `Literal`). Tightening the model (`extra="forbid"`, `Literal`) could reject existing stored seals; left as is. Related route-level note is in route_seals.md.
- seal.py:30-34: `compute_canonical_hash` raises `TypeError` for non-JSON values (datetime, set) in `metric_summary` at mint time. Fail-loud and deterministic; left unchanged (using `mode="json"` would make set hashing order-nondeterministic).
- models.py:59-88 (`EvidenceReceipt.create`): `receipt_digest` covers ids, spec/evaluator hashes, scores, promoted, reason and timestamp but not `input_hashes`, `false_positive_rate` or `metadata`, and there is no verifier for this receipt type. Changing the digest composition would alter stored digests and is a design/ADR question, so not changed.
- models.py:19-31 (`EvaluationResult`): numeric fields are unconstrained (denominator 0, negative counts, numerator > denominator, fpr outside [0,1] accepted). Producers (evaluator.py) always emit consistent values; not changed.
