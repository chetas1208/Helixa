# Audit: evolution (services/runtime/evolution/*)

Tests: `services/tests/test_audit_evolution.py` (no Mongo access). Each FIXED item below was reproduced as a failing test on the unmodified code (9 failures), then passed after the minimal fix.

## FIXED
1. services/runtime/evolution/candidate_search.py:32-72 (`generate_candidate_branches`): branches were deep copies of the parent that kept the parent's `parent_version_id` and `status` (BASELINE), so a candidate lost lineage and was labelled as a baseline. `MetaHarnessSearchAdapter` and `GepaProposerAdapter` set both. Test: `test_branches_record_lineage_and_candidate_status`. Fix: each branch sets `parent_version_id = parent.version_id` and `status = CANDIDATE` (the same values on every branch, so hash de-duplication is unchanged).
2. services/runtime/evolution/candidate_search.py:39 (branch 1 ignored `max_branches`; `max_branches=0` or negative still returned one branch). Tests: `test_bounded_search_honors_non_positive_max_branches[0,-1]`. Fix: branch 1 is appended only if `len(branches) < max_branches`.
3. services/runtime/evolution/search_adapter.py:37 (same defect for Variant 1 and `max_candidates`). Tests: `test_meta_harness_honors_non_positive_max_candidates[0,-1]`. Fix: same guard on Variant 1.
4. services/runtime/evolution/promotion.py:`evaluate_and_promote` (evidence not bound to the spec being promoted): `receipt` was unused and `eval_result.candidate_version_id` was never compared with `candidate_spec`, so spec X could be promoted on the strength of an evaluation of spec Y, or of a spec edited after evaluation. Tests: `test_promotion_rejects_evaluation_of_a_different_candidate`, `test_promotion_rejects_spec_that_differs_from_evaluated_spec`. Fix: new Gate 6 raises `PromotionGateError` unless `eval_result.candidate_version_id`, `receipt.candidate_version_id` equal `candidate_spec.version_id` and `receipt.candidate_spec_hash == candidate_spec.compute_spec_hash()`. It runs after gates 1-5, so earlier gate messages are unchanged.
5. services/runtime/evolution/promotion.py:`evaluate_and_promote` (documented "candidate score >= parent score" gate was never enforced; promotion trusted the `promoted` flag alone). Test: `test_promotion_rejects_score_below_parent_even_if_flag_set`. Fix: new Gate 5 compares scores by cross-multiplication. `IndependentEvaluator` only sets `promoted` when the candidate score is strictly higher, so legitimate results are unaffected.
6. services/runtime/evolution/promotion.py:`evaluate_and_promote` Gate 4 (fail-open when the evaluation carries no `heldout_transfer` case: an empty loop passed). Test: `test_promotion_requires_heldout_evidence`. Fix: Gate 4 raises if no held-out case is present. Held-out ids and fixtures are not touched (ADR-017 unchanged).

## UNVERIFIED/NEEDS OTHER OWNER
- promotion.py:59: `await self.harness_repo.promote_version(...)` calls a method that does not exist on `HarnessRepository` (services/integrations/mongodb/repositories/harness_eval.py has only save/get/list/get_lineage/record_mutation). Any caller that passes a real repo gets `AttributeError`. No caller in the repo passes a repo today. Owner: mongo_repo_rest. The docstring's "atomic CAS" promotion is not implemented in this module.
- promotion.py:28-62: no check that `eval_result.parent_version_id` equals `self.active_version_id`, and no lock between the awaited repo write and the pointer assignment. Two candidates evaluated against the same parent could both be promoted in sequence, the second overwriting the first without having been evaluated against it. Enforcing this would change the existing call contract (the test baseline id `harness-v1` differs from the default `harness-v1-baseline`), so it was not changed.
- promotion.py Gate 3: a result with no `negative_control` cases passes vacuously (gate 4 now fails closed, gate 3 was left as is, since the contract only requires "zero regressions").
- candidate_search.py:34-41: when `recommended_policy_action` is not one of the two mapped values (or the parent already satisfies it, e.g. any parent with the REF check on), branch 1 equals the parent's configuration and is emitted as a no-op candidate. Hash de-duplication compares only branches to each other, not to the parent. Filtering it would change branch counts that `test_v7_evolution_search.py` asserts (`len in (2, 3)`).
- candidate_search.py:33,46,59: `version_id` is `{parent}-branch-{focus|composite|retry}` rather than content-addressed (`stable_version_id`, ADR-020). Branch 1 differs by hypothesis but keeps the same id, so two different specs can share a `version_id` if persisted by id. Not persisted anywhere today.
- gepa_adapter.py:25-67 and search_adapter.py:52-74: a proposer can emit a candidate whose policy equals the parent's (empty `policy_diff`), e.g. the baseline with a REF incident only changes the REF check, but a parent already at `max_attempts_limit` makes Variant 2 a near no-op. Candidates inherit the parent's `metadata` (including a stale `parent_spec_hash` from `create_candidate_mutation`); metadata is excluded from the spec hash.
- optimizer_registry.py:50: `optimizers or list(...)` treats an explicit empty list as "all proposers"; unknown names are silently skipped (line 56). Intent is ambiguous, so left unchanged.
- optimizer_registry.py:38-73: outputs of a proposer added through `register_proposer` are not re-checked against the `PolicyEnvelope`; `PromotionAuthority` Gate 1 and `IndependentEvaluator` still reject out-of-envelope specs later. The de-duplication key `patch.canonical_hash` includes `version_id`, so semantically identical specs from different proposers are not merged.
- ADR-017: neither the registry nor the adapters call `assert_proposer_inputs_exclude_holdout`; the guard lives in services/runtime/v8/experiment.py:174 (owner v8_experiment), consistent with the ADR's stated limitation.

## VERIFIED OK
- Input specs are never mutated (all adapters deep-copy the parent); verified by existing tests and the lineage test.
- `gepa_package_status` / `scheduler_status`: report `DISABLED` on import failure, never call `optimize()`, and keep `primary_proposer` = `DETERMINISTIC` and `meta_harness_imported` = False (ADR-015).
- `optimizer_source` is always `DETERMINISTIC`; candidate ids come from `stable_version_id` in the two adapters (deterministic, no randomness).
- Envelope validation (`PolicyEnvelope.validate_candidate`) is applied to every candidate before it is emitted by all three generators, and `min(..., limit)` caps `max_attempts` / `max_context_items`.
- `PromotionAuthority`: gate 1 (envelope), gate 2 (`promoted` false returns False), gate 3 (negative-control regression) and the pointer update only after a successful repo write.
- Existing suites `test_v7_evolution_search.py`, `test_optimizer_gate.py` and the full `services/tests` suite pass after the changes.
